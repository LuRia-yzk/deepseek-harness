登记：super(ctx, 'fs') 到底做了什么

你已经找到"登记"那行代码了。这一页把它拆开，顺便说清 abstract 是什么。

01ctx 是一张表

把 ctx 想成一张两列的表：名字 → 东西。

名字（格子）里面放着的东西
fs一个 FileSystem 对象 —— 会真的读写文件的那个
tools工具注册表对象
llm模型适配器所在的对象
……
注意两列的区别：左列是名字（一段文字），右列是东西（能干活的对象）。
ctx.fs 读作"从表里按名字 fs 取出右边那个东西"。

02拆开这一行

super(ctx, 'fs')
super
"调用我父类的构造函数"。FileSystem extends Service，所以父类是 Service。真正干登记这件事的代码在 Service 里。
ctx
登记到哪张表上。
'fs'
用哪个名字挂。
为什么要加引号？因为它是名字，不是变量。不加引号的 fs 在代码里意思是"某个叫 fs 的变量"；加了引号的 'fs' 意思是"这七个字符本身"，也就是那个格子上的标签。
整句连起来：把"我"这个对象，以名字 fs 登记到 ctx 这张表上。
这就是你说的"把名字加到 ctx. 后面"——只不过做这件事的，是对象自己在出生的时候干的。

03abstract 是什么：说明书 vs 实现

说明书

packages/fs/fs

export abstract class FileSystem extends Service {
  abstract editText(...)
  abstract readText(...)
}

只写"必须要有哪些方法"，不写怎么做。
abstract 的意思就是：这里只有约定，没有实现。

实现

packages/fs/fs-local

class LocalFileSystem extends FileSystem {
  editText(...) {
    // 真的去改磁盘上的文件
  }
}

真的动手的代码。
换一个后端（远程沙箱），只需要另写一份实现，说明书不用动。

所以 editText 住在 packages/fs/fs 里，是说明书上的一个条目；
而"真正去改文件的那份代码"住在 packages/fs/fs-local 里。

04消费方怎么用

await ctx.fs.editText(...)
     └─┬─┘ └──┬───┘
       │      └─ 调用那个对象上的方法
       └─ 按名字 fs 从表里取出对象
edit.ts 从没 import 过任何 fs 的实现。它只是按名字取东西——
至于那个格子里此刻放的是本地实现还是远程实现，它不知道，也不需要知道。
留给你对比的两个名字：
提供 fs 的那个插件，包名是 @deepseek-ai/dsh-fs-local。
它登记到 ctx 上的格子名，是 fs。
