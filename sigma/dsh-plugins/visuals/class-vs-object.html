类 vs 对象 vs 继承

你这三个问题问到地基了。这一页是整个 DSH 插件体系里最基础的一块砖。

01两个世界

类（class）对象（object / 实例）
是什么模具、模板、图纸模具压出来的产品
住在哪源码里（.ts 文件的一段定义）内存里（程序跑起来之后才有）
有几个写一次就一个想要几个造几个
怎么来class X { }new X()
dsh 里的例子LocalFileSystemctx.fs 格子里那个东西
模具压完还在。new 不会消耗掉类——你可以用同一个类 new 出无数个对象。

02继承只发生在「类」和「类」之间

Service  ← 类（框架给的）
  ↑ extends
FileSystem  ← 类（说明书）
  ↑ extends
LocalFileSystem  ← 类（实现）
这三个全都是类，全都是模具。继承是"模具套模具"——子类模具 = 父类模具 + 自己的补充。

没有"继承一个对象"这回事。所以 `LocalFileSystem` 不是"子类的对象"，它本身就是一个类，只是这个类的模具是从上面两个模具叠出来的。

03new LocalFileSystem(ctx) 这一下，到底发生了五件事

拿 LocalFileSystem 这个模具准备压一个产品。
发现它没有自己的构造函数——所以沿用 FileSystem 的。
FileSystem 的构造函数第一句是 super(ctx, 'fs')——把活转交给 Service，并且自己填上名字 'fs'。
Service 的构造函数最后一句 ctx.reflect.provide('fs', self, ...)——把刚造出的对象登记到 ctx 上，然后 return self。
于是：ctx 上多了一个叫 fs 的格子，格子里放着这个新对象。

04回答你的四个问题

FileSystem 这个模板呢？ 还在。它只是源码里的一个类定义，`new` 不会消耗它。模具压完还在，随时可以再压。（在 dsh 的运行里它通常只被压一次，但语言层面不限制。）
为什么还要加 ctx 参数？ 因为登记要有目的地。一个程序里可能不止一个 ctx（Host 端一棵树、Client 端另一棵）。所以 ctx 不能写死，必须由外面传进来。
名字 name 怎么算？ 写死的，不是算出来的。就在 FileSystem 的构造函数里：super(ctx, 'fs')。它把 'fs' 这个字符串直接交给父类。
LocalFileSystem 这个名字在哪？ 只在源码里。运行时 ctx 上的格子叫 fs，跟 LocalFileSystem 没有任何关系。这个名字对人（读代码的、看报错的）有用，对"登记"没用。
把这三句话背下来，地基就成了：

① 类是模具，对象是产品。new = 压一次。
② 继承发生在类之间，不发生在对象之间。
③ 登记的"名字"是写死的字符串（'fs'），和类名、包名都没有关系。
